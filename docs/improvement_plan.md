# ELT Bench 提交前改进计划

目标是在2026年10月12日周一前形成可靠、可复现、能解释设计理由的交付版本。先修复已经复现的环境接口问题，再评估一个可关闭的反馈改进。官方任务、源数据、终局评分及训练目标保持固定；这份计划尚未作为新的实验结果。

采用小提交、自动化测试、隔离测试环境、小规模试运行和明确回退方式。这个做法参考 [Google SRE 发布工程与 canary 原则](https://sre.google/workbook/canarying-releases/) 和 [GitHub 检查门禁](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。本项目用专用测试 warehouse 做受控试运行，没有生产用户流量，不将其描述成已经部署的生产 canary。

## 当前基线和指标

已验证代码基线是 `9def90c867f2f11f7122952b819e282970d2d714`。2026年10月10日的文档修订尚未提交，不改变代码和既有实验结果。新增实现使用 `codex/reliability-feedback` 分支，文档校正、接口修复和反馈实验分开提交，保留原始材料及失败记录。

9B单条基线提交后为13/16列正确；四条更新前训练采样分别为未提交、14/16、未提交、15/16。该组提交2/4，完整任务正确0/4；51次transform尝试仅8次执行成功，其中11次因目标表使用逻辑models限定名被拒。样本小，不能作为模型总体成功率估计。

| 指标 | 用途和定义 |
|---|---|
| 完整任务正确率 | 主指标；有效rollout中，显式提交、加载完整、独立重放后两张输出均通过官方比较的比例 |
| 提交率 | 有效rollout中显式提交pipeline的比例，区分未完成与结果错误 |
| 平均终局reward | 包含未提交的0分，衡量部分正确性；同时报告已提交轨迹的正确列数，不只展示最好成绩 |
| 无效与重复操作 | 分开统计SQL语法/语义错误、接口误拒绝、重复错误和重复查询；不能把所有失败归因于模型 |
| 基础设施无效率 | 连接、源服务、资源和清理故障单列；不能作为0分模型样本，不能从报告中隐去 |
| 成本与耗时 | 记录生成token、保守预留、可取得的实际费用、抽取/加载/SQL/重放/评分/总体耗时；重叠计时不相加 |

耗时先报告单次、中位数和范围；少量云样本不用于声称稳定的p95。零个完整成功时，不计算或伪造“每次成功成本”。既有一次RL更新只证明训练链路完成，更新后效果评估是另一个实验。

## 第一步 建立可复现的问题清单

将已保存轨迹中的问题按类别建成小清单，每项包含触发输入、实际行为、期望行为、最小复现和证据路径。

| 类别 | 当前例子 | 处理原则 |
|---|---|---|
| 环境接口缺陷 | models.trucks误拒绝、TO_DATE的AST名称与白名单不一致、日期反馈为epoch-ms | 优先修复共同入口，并补针对该失败的回归测试 |
| 模型动作错误 | SQL语法/字段引用错误、收货客户被理解为司机、公司名筛选字段选错、错列名 | 返回准确反馈，让模型自行修正；不代写正确SQL或隐式提交 |
| 基础设施故障 | 源服务缺失、连接失败、清理失败 | 修复或停止该组；保持invalid语义和原预算门禁 |

来源：`runs/sql_interface_diagnosis_20261010.json`、`runs/optimization_diagnosis_20261010.json`、原始grade/tool_trace/messages。安全泄漏、错误高分、重复训练计费属于必须阻止交付的问题；此次重点修复有明确复现的正常SQL误拒绝，不扩大到任意SQL支持。

## 第二步 修复接口并统一基础反馈

修改集中在已有warehouse、Episode和cookbook连接处，优先复用现有函数和依赖。

1. 允许未限定输出名及逻辑 `models.<requested_model>`，将两者安全映射到本episode模型schema。继续拒绝raw写入、其他schema、显式catalog、外部文件和多语句。
2. 修复TO_DATE内部canonical名称不匹配。FIRST_VALUE、EXISTS等只按shipping所需的纯查询用法逐项验证和纳入；不全面放开函数白名单，不允许UDF或外部I/O。
3. 查询日期使用ISO格式，区分DATE与TIMESTAMP并保留NULL；有时区时保留实际时区，不给无时区值凭空添加UTC。需要类型反馈时取实际destination元数据，区分仓库类型和pandas dtype，不把声明类型冒充实际类型。
4. 明确操作成功、动作错误、策略拒绝和基础设施故障。错误消息保持脱敏和长度限制；涉及字段/关系只从公开任务和当前episode状态产生。
5. 在现有反馈中显示已加载源、已执行模型和工具预算余量。已创建表不等于列值正确。轮数/token余量只有控制器提供真实计数时才显示，不用工具调用数估算模型轮数。保持显式submit，不自动提交。

通过条件：已复现的正常操作不再被误拒，所有原安全反例仍被拒，日期反馈与实际值一致，正确/错误/未提交/基础设施故障的reward语义保持不变。该步骤是接口可靠性修复；即使后续模型表现改善，也不将它包装成新RL算法。

## 第三步 建立自动化检查门禁

先运行针对本次修复的最小测试，再运行现有完整回归。保留原测试，不通过削弱测试放行。核心检查包括：

- 合法逻辑目标、日期、窗口/子查询用法以及对应跨schema、多语句、文件/URL、raw写入反例。
- 正确与错误pipeline的独立进程重放、NULL/重复行/类型行为、未提交及恒定reward组。
- 原cookbook轨迹转换、采样logprobs和训练mask；单位测试中的API替代对象只用于检查控制逻辑，不计作真实云验收。
- SQL AST与受限数据库权限继续共同生效；共享ELT_AGENT的跨episode数据库角色隔离局限保留在文档，不因通过本地测试宣称已经消除。

运行现有入口：

```powershell
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/ruff.exe check elt_tinker tests scripts infra
.venv/Scripts/python.exe -m build
.venv/Scripts/python.exe -m elt_tinker.local_integration --output runs/local_candidate_01
```

实际执行时使用尚不存在的output目录。安装验证使用新venv和已构建wheel；本地integration不能依赖测试模块、当前Episode缓存或操作者私有路径。复用 `scripts/benchmark_local.py` 对同一fixture做前后测量，不声称未测出的云端加速。

补一个最小GitHub Actions工作流运行无凭据核心检查和构建。cookbook全套与真实Snowflake检查单独记录环境和结果；若CI跳过可选测试，报告skip数量，不冒称完整回归均已在CI运行。PR说明写清触发问题、行为变化、验证和限制。支持强制branch检查时启用；否则仍以检查通过作为合并条件，不为此增加付费平台。

复杂控制流出现时按code-simplification做本次修改范围内的审查；最后静态审查以该分支相对基线的diff为范围。任何安全、评分或资源门禁回归必须先修复。

## 第四步 单独评估公开字段覆盖反馈

候选机制是成功transform后，比较实际输出字段与公开要求，提示缺少、重复或额外字段。比较大小写规则与官方要求一致；额外列保持官方允许规则，不额外扣分。反馈不能访问hidden参考、给出正确数值或替模型修改pipeline，也不新增过程奖励。

只加一个明确的开关，复用原transform反馈，不新增工具或框架。读取实际schema若增加数据库请求，单独记录I/O和耗时。必须测试缺列、错名、正确字段、额外列、空表、重复调用，以及提示内容不包含hidden参考。字段覆盖只能发现契约问题，不能保证业务语义和值正确。

该实验比较两个版本：

- A：第二步已修复的环境，字段覆盖反馈关闭。
- B：同一修复版，字段覆盖反馈开启。

两者共享同一个固定模型/sampler checkpoint，不在A/B之间更新参数；固定shipping版本、源数据、官方reward、renderer、采样参数、工具/轮数/token限制和并发设置。API支持seed时保存它，仍保留生成的实际轨迹。按A/B交替顺序运行，避免时间或源服务差异集中在一组。不能直接把旧4B成绩与新9B成绩作对照。

真实试运行先检查源内容、Snowflake权限、独立schema与清理，以及共享预算保守估算。先一对小样本检查链路；预算允许时目标每版本4条，全部保留并报告。样本不足时只称初步观察或冒烟检查，不证明普遍成功率提升。历史动作离线复现仅能证明接口行为变化，不能替代模型驱动对照。

当前保守预留约US$7.735，上限US$10；约US$2.265差额不是服务端余额。新对照能否完成必须先算共同预算，保留失败预留，不能更换账本绕过上限或自动增加费用。Snowflake仍仅使用有效试用额度。如果不足以覆盖两个版本，就完成本地修复与反馈验证，明确真实效果尚未验证。

只有安全/评分/训练语义回归全部通过，才考虑采纳新反馈。主要观察完整任务正确率与提交率，再用字段错误、重复调用及耗时解释结果。若收益不明确或成本增加无法解释，交付可靠修复版，并保留反馈为默认关闭的实验选项或暂缓加入。
